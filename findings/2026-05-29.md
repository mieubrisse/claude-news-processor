### Workflows / Subagent Orchestration

**1. Decide how Dynamic Workflows relates to your `subagent-driven-development` mandate.**
- **What:** Add a routing note to `subagent-driven-development` (or your superpowers preferences block in CLAUDE.md) distinguishing when to use native Dynamic Workflows vs. your current skill-driven subagent execution.
- **Why:** Dynamic Workflows is a *native* version of the thing your config already mandates manually — parallel subagents with independent verification and adversarial refutation before convergence. This is the closest overlap with your core workflow of any post this batch. Right now your CLAUDE.md says "always use subagent-driven-development"; a new first-party primitive now competes for that slot, and an unguided agent won't know which to reach for.
- **How:** The natural split: keep `subagent-driven-development` (plan-driven, you control the task decomposition, predictable token cost) as the default for normal feature work; reserve Dynamic Workflows for the large-fan-out cases the post highlights — whole-codebase audits, sweeping migrations across thousands of files, adversarial verification — where you *want* Claude to author the orchestration itself. Note the token-cost caveat explicitly so it isn't reached for casually. The `ultracode` auto-decide setting is probably the wrong default for you given the cost; prefer explicit invocation.
- **Impact:** High — touches your single most-used engineering workflow.
- **Confidence:** Likely. Crux: whether Dynamic Workflows is enabled on your Max plan (admin-gated) and whether its token cost is acceptable for your usage. Worth a small live test before committing a rule.

**2. Adopt the "blind verifier" pattern in your review/verification subagents.**
- **What:** When spawning a verification or code-review subagent (`requesting-code-review`, `verification-before-completion`, or the security loop below), withhold the *reasoning* of the agent that produced the work — give the verifier only the artifact and the spec, not the author's justification.
- **Why:** Both the security post and CodeRabbit independently land on this: independent agents that can't see the originator's reasoning catch confirmation-bias errors the author rationalized away. This is the same failure your CLAUDE.md "Truth-Seeking Partnership" / "Authorship is not evidence of correctness" rule fights — and a clean structural way to enforce it via context isolation rather than willpower.
- **How:** In the relevant skills, instruct the spawn prompt to pass the changed files + the original spec/task, and explicitly *not* paste the implementing agent's chain-of-thought or self-assessment.
- **Impact:** Medium-High — generalizes beyond security to all your review gates.
- **Confidence:** Likely.
