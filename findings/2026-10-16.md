### The new source: claude.dev/blog

Ten posts, none previously processed. Dates are the blog's own, which disagree with `claude.com`'s curation dates for the same posts.

**[Building effective agent automations](https://claude.dev/blog/building-effective-agent-automations/)** (Oct 6) The most useful post in this window. It is a reference implementation for scheduled unattended agents, and it independently derives several rules your own config already carries while going further on three. The mechanism is per-source **bookmarks** in a state file rather than fixed time windows, because "a late run leaves a gap and an early run repeats items." On a source that silently fails: keep that source's bookmark unchanged, write the brief from working sources only, and "end the brief with one line naming what it couldn't read." On delivery: "the post counts as sent only if Slack returns `ok: true` and a message ts," and only then update the ledger and bookmarks, with the run record marked `posting` → `posted` or `maybe posted`. It also splits memory into **preferences** (read-only to the agent) and **state** (read-write), caps spend with a `budget` in cents that halts the run with a `budget_reached` stop reason, and insists dates be computed in the reader's timezone, not the server's.

**[Automating eval design and hillclimbing with Claude](https://claude.dev/blog/automating-eval-design-and-hillclimbing/)** (Sep 28) The mechanism behind two CLI subcommands you already have on disk. `/claude-api build-eval` samples eval inputs in priority order (production transcripts, then bug reports, then 5–10 hand-written cases, then synthetic cases anchored to real ones), proposes the cheapest grader that fits the output space, and validates it with three diagnostics: it runs the grader twice on identical outputs to detect verdict variance, checks for timeouts and API errors, and warns when baseline scores exceed about 95% because there is no headroom left to measure. `/claude-api hillclimb` splits the set into train and test, then each round reads only train-set failures, proposes one targeted patch, and reverts it if train improves while test stays flat — "Claude suspects overfitting and reverts the patch." The anti-leak rule is explicit: "Never paste failures into the prompt." When scores plateau for two or three rounds it stops patching and sorts the remaining failures by root cause instead, separating genuine misses from ambiguous tasks, harness errors, and grader miscalibration. It reports confidence intervals and recommends against merging when gains fall inside the noise margin. Worked example: 78.6% → 90.5% on held-out tickets, cost per ticket 4.6¢ → ~1¢.

**[How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic/)** (Oct 8) A seven-layer pipeline, of which two parts transfer directly. First, findings are produced by **parallel agents and then voted on by a separate group**: "Several agents look for bugs at the same time. Then a separate group votes on each finding, and it only gets posted if enough of them agree it's real." Second, and the part you do not have anywhere: they **measure their reviewer's noise** by sorting "every comment the reviewer leaves by how the person on the PR responded: they fixed it, said it was wrong, said the behavior was intentional, or decided it didn't matter." Convergence is enforced with a round cap after three passes, diff-only re-review afterward, and no repeated findings. Style, diagnostic, and cleanup findings are dropped outright; survivors are tagged Important, Nit, or Pre-existing. Human approval scales with change risk (zero, one, or two people), not with author. The reviewer runs daily against an eval set built from real past incidents.

**[Claude Code in the cloud: a field guide to cloud sessions](https://claude.dev/blog/claude-code-in-the-cloud/)** (Oct 1) Each task gets "a fresh VM with your repository cloned onto a new claude branch," roughly 4 vCPUs, 16 GB RAM, 30 GB disk, with the GitHub token held by a proxy outside the VM. Launch via `claude --cloud "task"`, the web app, mobile, Slack, or **Routines** — scheduled or webhook-triggered runs that "run without approval prompts," minimum hourly cadence, pushing to `claude/`-prefixed branches. Follow-ups go to a running session with `claude -p "instruction" --cloud <session-id>`; `claude --teleport <session-id>` pulls the branch and the whole conversation down locally. The comparison table is blunt about the thing that has been breaking your cron: local "stops when laptop sleeps/disconnects," cloud "continues while user away." The load-bearing limitation for you: "Repository-level `.claude/` settings, `CLAUDE.md`, skills, and agents travel to the cloud VM, but personal `~/.claude` config does not."

**[Getting started with Claude Code mods](https://claude.dev/blog/getting-started-with-claude-code-mods/)** (Sep 28) The mechanism, now that you can reach it. A mod is a JS/TS module packaged as a plugin, declared in `hooks/hooks.json` as `{"modules": ["./x.mjs"]}`, exporting `register(on, options)`. Hooks take the signature `on(eventName, matcher?, async ($, e, next) => ...)` and chain like middleware, with three behaviors: observe (`const r = await next(e)`), **rewrite** (`return next({ ...e, command: modified })`), and answer (`return { deny: "reason" }` without calling `next`). Interceptable events include `session.start`, `turn.complete`, `tool.call` (filterable, e.g. `{ tool: "Bash" }`), `prompt.submit`, `command.run`, `ui.render`, and `session.usage`. The `$` API exposes `$.session.usage()` for live context metrics, `$.state.get/set()` for state that survives hot reload, `$.ui.*` for drawing terminal and desktop components, `$.process.run()`, `$.command.register()`, `$.tool`, and `$.model`. Two commands matter beyond the mod itself: `claude plugin validate` checks the manifest and state declarations, and **`claude plugin test` runs TypeScript tests against a real Claude Code runtime**. The contrast with what you run today is stated directly: "A settings hook runs a shell command for each event and passes JSON over stdin and stdout. A mod is loaded once and stays in the session." Security caveat: mods are unsandboxed, "written by its publisher, not Anthropic."

**[Using Claude Code: Spending your effort](https://claude.dev/blog/spending-your-effort/)** (Sep 25) Effort is a compute budget with levels low, medium, high, xhigh, max, and "higher effort will involve Claude taking more independent action for judgement and verification." The author's own allocation: low "for quick responses that are in the loop, e.g. brainstorming, sketching, easy changes," medium "for most of my regular software engineering work," high "for work where verification is important or there are edge cases," max "when I want Claude to operate fully autonomously to solve difficult problems." Higher effort costs 2–3x the tokens; Terminal-Bench 3.0 data shows "same score, half the tokens" at lower levels on some tasks. It does **not** address whether a model-pinned hook inherits a globally configured effort level — the question `notes.md` has carried since 2026-09-11.
