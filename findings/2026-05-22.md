Suggested Improvements
----------------------

### Workflows — HTML output as a deliberate option (NOT a default flip)

**What:** Decide whether to introduce HTML as a *selectable* output format for a small set of specific skills, without breaking the existing markdown convention.

**Why:** The blog post argues HTML is dramatically better for (a) side-by-side comparison of multiple options, (b) annotated diff/review reports, (c) interactive parameter tuning with export-back-to-prompt buttons, and (d) shareable dashboards. The user's current setup uses markdown for everything, including outputs where these benefits would land — e.g., `/brainstorm` (option-comparison), code-review subagent output, `/weekly-plan` rollups, `/todays-work` summaries. The user's CLAUDE.md mandates setext-style markdown headers, which is a *style* convention for prose markdown — it does not preclude HTML artifacts for cases where HTML is the better medium.

**How:**
1. Identify candidate skills where HTML would genuinely win — not "everywhere," but specific cases: `/brainstorm` divergent option grids, `/code-reviewer` annotated diffs, possibly `/weekly-plan` rollups, possibly `/todays-work` summaries.
2. For each candidate, decide if HTML output should be the default, an opt-in flag, or remain markdown.
3. Keep the existing markdown rule unchanged — it governs prose; HTML artifacts are a different surface.

**Impact:** Medium. Real productivity gain on comparison/review/dashboard surfaces. Risk: cargo-culting HTML everywhere when markdown is sufficient (skill discipline matters).

**Confidence:** Likely. The post is from an Anthropic engineer making a strong claim, but adoption depends on whether the user actually wants to consume HTML artifacts vs. plain markdown in their daily flow.

### Workflows — "Overnight historically-deferred project" framing

**What:** Adopt the explicit framing that *historically-deferred analytical projects can now be one-shot overnight runs* — not as a new skill, but as a mental pattern surfaced in `/focus-and-prioritization` or a content-strategy/venture-strategy skill.

**Why:** The Bryant piece's killer example is scoring 4,000 accounts overnight against a five-dimension rubric — work that would historically take hundreds of cross-functional hours. The user has analogous deferred projects in their venture work: ICP segmentation, content-piece scoring against resonance criteria, retroactive analysis of past content performance, competitor landscape scans. The user already has `/schedule` and runs cron-like missions (this very repo). What's missing is the *trigger* — a framing that turns "this analytical project is too big" into "this is an overnight run."

**How:** Add a short section to `/focus-and-prioritization` (or wherever the user catalogs unblocked-work patterns) naming this pattern explicitly: "Project too big to do manually but well-defined? Define the rubric, test on one subset, schedule overnight." Reference the Bryant post.

**Impact:** Medium. Mostly a framing change, but framings unlock work.

**Confidence:** Likely.
