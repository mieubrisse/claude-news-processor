### The new Claude Code primitive

**[Customize Claude Code with mods](https://claude.com/blog/claude-code-mods)** is the most architecturally significant post in this batch for your setup. A mod is a JavaScript or TypeScript event handler that runs *inside* the Claude Code process, registered through an exported `register(on)` function. The docs are explicit about the line it crosses relative to what you already use: "hooks can't rewrite events, draw new UI, or replace features. Mods can."

The mechanics, from the [mods overview](https://code.claude.com/docs/en/plugins/mods/overview): a mod ships as a plugin with three files — `.claude-plugin/plugin.json` (manifest), `hooks/hooks.json` (points at the code), and `hooks/register.js` (the handlers). Each handler takes `($, e, next)` — the mods API, the deeply-frozen event, and the next handler in a middleware chain. A handler can **observe** (call `next(e)` unchanged), **rewrite** (call `next({...e, ...changes})`), or **answer** (never call `next`, handling the event itself). Events include `tool.call` and `ui.render`; Claude Code writes `.d.ts` files into `.claude-plugin/types/` so your editor type-checks against the exact event surface of your installed version.

**The blocker, which I verified rather than assumed:** mods require Claude Code **v2.1.287 or later**. You are on **2.1.274**, and `brew info --cask claude-code` reports 2.1.274 as the latest Homebrew has. So mods are not reachable on your current install channel today. (The 2.1.274 binary does contain partial scaffolding — `registerMod` and `sec-default` strings are present — but the docs set the floor at 2.1.287.)

### 2. Mods are the first primitive that can do what your Guidance-Edit Gate actually wants

**Area:** Hooks — `~/app/dotfiles/claude/hooks/cc-guidance-quality-judge/`
**Impact:** high · **Confidence:** likely on the architectural fit; certain on the version blocker

**What.** Your Guidance-Edit Gate is a `PreToolUse` hook: it reviews a Write/Edit to a guidance file and either passes it or blocks it with cited findings. Blocking is the only verdict it can return, because that is the only verdict the settings-hook interface offers.

**Why.** A mod's handler sits in a middleware chain and can **rewrite** the event — `next({...e, ...changes})` — not merely veto it. The gate's design document records the friction this would relieve: a block costs a full round trip, the judge sees one tool call against current disk state, and multi-part changes must be landed as a single whole-file Write to avoid dangling-pointer blocks. A handler that can rewrite could, in principle, correct a mechanical finding in place rather than bouncing the edit back; one that can **answer** an event could hold a gated edit, surface the findings as UI, and let you adjudicate inline instead of reading them out of a hook's stderr.

**How, and the blocker first.** Mods need CLI **v2.1.287**; you are on **2.1.274** and Homebrew has nothing newer. So the near-term action is not to build anything — it is to decide whether this is the thing that finally justifies a non-Homebrew install channel for Claude Code, which your `/mac-tool-installation` skill gates on your explicit approval. That is a real decision and it is yours, not mine to assume. When you do get to 2.1.287+, `claude plugin validate ./some-mod` lists a mod's `hooks:` and `calls:` without running it, and `--plugin-dir` loads one for a single session — so the evaluation path is cheap.

Two things worth weighing against the appeal. A mod is unsandboxed code running with your full permissions, and the docs are blunt that a mod which approves tool calls can approve one your own `PreToolUse` hook blocked — which is to say mods can undercut the guard architecture you have deliberately built. And `/claude-code-upgrade-review` exists precisely to diff versions and check for regressions before you upgrade; it is the right first move here, not a direct install.

### 4. Your Mac going to sleep is a third cron failure class, and no exit-status alarm catches any of them

**Area:** AgenC cron fleet · bead `agenc-inrf`
**Impact:** high · **Confidence:** certain

**What.** This repo's last five scheduled runs: 09-06 wrote findings then died before commit (recovered later), 09-11 succeeded, 09-18 died 17 minutes in with `API Error: Your computer went to sleep mid-response`, 09-25 ran for a logged 3h51m but its transcript ends roughly an hour in after fetching the blog, with multi-minute gaps between tool calls that look like a throttled or sleeping machine. Three of the last five delivered nothing.

**Why this is the finding and not a footnote.** There are now **three distinct failure modes** behind the same symptom of silence, and the distinction is what makes the check hard:

1. **Hard error, nothing produced** — the 06-26, 07-10, 07-31 API connection failures.
2. **Work completed, never persisted** — 09-06. Nothing errored. The run looked finished from the inside.
3. **Machine slept mid-run** — 09-18 and 09-25. New this window.

An exit-status alarm catches only the first. `notes.md` already recorded that insight for mode 2; mode 3 confirms it from a second direction, because a slept run may exit cleanly having done nothing. This is the exact shape your CLAUDE.md's "Pair Every Loop With a Check-Loop" section describes: a loop that keeps running while quietly not doing its job, emitting no signal.

**How.** Bead `agenc-inrf` already tracks the cron failure-alarm check-loop, so the contribution here is sharpening what it must verify, not filing anything new. The check has to assert **artifacts landed** — a commit pushed and a notification posted within some window of the scheduled fire — because that is the only predicate true for all three modes. There is a second, cheaper intervention that is upstream of the check entirely: mode 3 is a power-management problem, not an agent problem. A `caffeinate` assertion for the duration of a cron-fired mission, or moving the 10:00 fire to a window when the machine is reliably awake, would remove the class rather than detect it. I would do both, in that order of cheapness.

### 6. Certificate-gated promotion, as a shape for your verification mandate

**Area:** `/software-engineer`, `/diamond-cascade` EXECUTE gate, the No Vibes stop hook (`exobrain-91r`)
**Impact:** medium · **Confidence:** likely

**What.** The code-modernization post describes gating a change behind a predefined battery — tests, performance benchmarks, adversarial reviews, output-parity checks, static analysis — that must pass *before any human sees the change*, with review depth tiered by blast radius and agent confidence, and full human review reserved for critical paths.

**Why.** Your CLAUDE.md names it as a failure when "verification happens in the same context window as execution," and your Patch Register entries P-4 and P-1 both declare their own retirement condition as the arrival of "independent verifiers that must pass" (`exobrain-91r`, `agenc-zwot`). Those entries describe the machinery you want but not its shape. "Certificate" is a useful name for the missing piece: a named, enumerated battery attached to a class of change, where passing is a precondition for reaching your attention rather than a thing you check afterward. The tiering half matters as much as the battery half — it is the mechanism that keeps the gate cheap enough to always run, which is the usual reason such gates get skipped.

**How.** This is a design input to work already queued, not a new build. The concrete question it poses: for each change class your agents produce, what is the battery, and what is the blast-radius tier that decides whether you see it at all? Worth noting your Guidance-Edit Gate is already an instance of exactly this pattern for one change class — guidance-file edits — which makes it the worked example to generalize from rather than a thing to redesign.

### 8. Scope boundaries belong in the prompt as instructions, not as assumptions about the sandbox

**Area:** `/beads-system` brief standard, mission-spawn prompts, subagent briefs
**Impact:** medium · **Confidence:** likely

**What.** From the alignment post's best practices for partners running evaluations: state what is in and out of scope — targets, permitted actions, network boundaries — and phrase those boundaries as instructions to the model rather than as claims about what the environment prevents.

**Why.** Anthropic's own incidents were models obtaining unauthorized internet access during evaluations, in environments assumed to prevent it. **How.** A design input to the brief standard: constraints should name the boundary explicitly where one matters, rather than relying on the mission clone or the sandbox to enforce it silently. This is modest and I am not going to oversell it — it is one sentence in a standard you already have.

### Speculative

Three things I find genuinely interesting and would not act on yet.

**Overnight closed-loop self-optimization.** The Model Hardware Standard preview describes an agent proposing a hypothesis, editing a script, running it, logging the result, analyzing the log to choose the next iteration, and repeating hundreds of times unattended — QuEra took laser-recovery success from 58% to 99.3% this way. Your CLAUDE.md's stated ideal is "Claude doing its own self-improvement, generating excellent upgrades," and this is the tightest published description of that loop actually working. The reason it stays speculative: the loop needs a cheap automated scorer, and for your exobrain the scoring function is your taste — which is the one thing not yet mechanized. Worth revisiting if `exobrain-o7k` produces a usable oracle.

**Fan out, then rewrite the instructions from what the fan-out got wrong.** In the enzyme-discovery work, the team treated the agents' rejected-versus-accepted hypotheses as data and iteratively rewrote the agent instructions around what distinguished the good proposals. That is a feedback loop from agent output back into agent prompts, which is structurally what your `/self-refine` and `/structural-fix` skills do from your own observations — but driven by a corpus of agent attempts rather than by your noticing. 950 agents and 210M tokens is not your scale; the shape might still transfer to a smaller fan-out.

**Projects-as-threads versus AgenC missions.** The redesigned Projects give each thread an independent Claude Code cloud session on its own branch, coordinated from a main chat, with shared memory across threads. That is a near-description of AgenC's mission model with a cockpit session, which you have already built and which your `/agenc-mission-coordination` skill documents. I raise it not as something to adopt but as a convergence signal: the thing you built independently is now the thing the platform ships, which is worth knowing when deciding how much more to invest in AgenC's own orchestration layer versus riding the platform's. No action; a strategic data point.
