Blog Digest

**[How Anthropic enables self-service data analytics with Claude](https://claude.com/blog/how-anthropic-enables-self-service-data-analytics-with-claude)** — Anthropic automated 95% of business analytics queries via a skill-augmented Claude. The post identifies three failure modes (concept-to-entity ambiguity, data staleness, retrieval failure) and prescribes layered "sources of truth" (semantic layer, lineage, curated docs, business context), pairwise knowledge/unbook skills, offline+ablation evals, and correction-harvesting via PR automation. Headline data point: "Without skills, Claude's ability to answer analytics questions accurately didn't exceed 21%. Adding skills gets these numbers consistently above 95%."

**[Lessons from building Claude Code: How we use skills](https://claude.com/blog/lessons-from-building-claude-code-how-we-use-skills)** — Internal lessons from Anthropic's hundreds of active skills. Nine skill categories (library reference, verification, data fetching, business process, scaffolding, code quality, CI/CD, runbooks, infra ops). Core principles: avoid restating what Claude already knows, lead with a "Gotchas section" as highest-signal content, use progressive disclosure via folder structure, avoid railroading, write descriptions for the selection model (include activation phrases). Concrete techniques: `config.json` for user settings, append-only logs for skill memory, on-demand hooks like `/careful` that block destructive commands during production work, `PreToolUse` hooks to log skill invocations and measure popularity.

**[Best practices for getting started with Claude Cowork](https://claude.com/blog/best-practices-for-getting-started-with-claude-cowork)** — Positioning piece for Cowork (the no-code multi-step delegation workspace, distinct from Claude Code). Five criteria to identify Cowork-suitable tasks (multiple inputs, file outputs, recurring, clear quality bar, tedious middle steps). Standout best practice: have the agent repeat the ask back and ask clarifying questions before starting. Recommends beginning with one repetitive weekly task in a domain where you can immediately judge output quality.

**[Running an AI-native engineering org](https://claude.com/blog/running-an-ai-native-engineering-org)** — Fiona Fung (Director of Engineering, Claude Code) on org-level process changes once agentic coding becomes default. Bottleneck shifts from code-writing to verification/review/security. Replace six-month roadmaps with JIT planning. Ask Claude instead of finding original authors, then automate recurring queries. Humans focus on security, legal, product decisions, taste; Claude handles style, linting, bugs. Track ramp time, PR cycle time, % Claude-assisted commits. Heuristic: "Pick your noisiest workflow" and ask whether it still serves, can be automated, or should be killed.

**[A harness for every task: Dynamic workflows in Claude Code](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code)** — Companion to the earlier dynamic-workflows announcement (processed 2026-05-29). Names six reusable orchestration patterns: (1) classify-and-act, (2) fan-out-and-synthesize, (3) adversarial verification, (4) generate-and-filter, (5) tournament, (6) loop-until-done. Identifies the failure modes workflows fix: agentic laziness, self-preferential bias, goal drift. Recommends explicit token budgets per subagent, saving workflows to `~/.claude/workflows`, distributing via skills, and combining with `/goal` and `/loop`. Reserve workflows for high-value tasks (research, security, fact-checking, migrations, triage at scale, model routing).

### Skills

**[High impact, Likely]** Audit skills for a dedicated "Gotchas" section. The Anthropic post calls this "the highest-signal content in any skill" and says effective skills "began with a few lines and a single gotcha." Kevin's skill library is extensive (200+ skills), and while many already encode warnings, few have an explicitly-marked Gotchas section that survives reorganization. Spawn a dotfiles mission to audit a representative sample (e.g., the language-specific skills `/go-coding`, `/typescript-coding`, `/python-coding`, `/bash-coding` and a few process skills like `/process-meeting`, `/log-venture-repo-conversation`) and propose a "Gotchas" convention if one doesn't exist. This complements — does not duplicate — Kevin's existing provenance footers, which capture *why* a rule was added, not the *what* a future agent will trip on.

- **What:** Convention for a `Gotchas` (or equivalent) section near the top of skills where novel failure modes accumulate.
- **Why:** Anthropic's flagship advice from their skill-building post; signal-density beats prose volume.
- **How:** Dotfiles mission to survey existing skills and propose either a convention update to `/cc-skill-management` or a documented pattern in the global CLAUDE.md skill-writing guidance.
- **Impact:** High — applies to every existing and future skill.
- **Confidence:** Likely — Kevin may already do this implicitly; the question is whether an explicit convention pays for itself.

**[High impact, Likely]** Add a `PreToolUse` hook that logs `Skill` invocations to identify under-triggered or over-triggered skills. Anthropic uses this exact pattern to measure skill popularity. Kevin has a sprawling library and no current way to know which skills actually fire vs. which are dead weight. A logging hook would surface (a) skills that never get invoked despite being present, (b) skills invoked under wrong conditions, (c) workflows where Claude reaches for a tool when a skill would serve better.

- **What:** A `PreToolUse` hook matched on the `Skill` tool that appends `{timestamp, mission_uuid, skill_name}` to a log file (e.g., `~/.agenc/logs/skill-invocations.jsonl`).
- **Why:** The "Skill-First Reach" rule in Kevin's CLAUDE.md targets the failure of bypassing skills; measurement would tell him whether the rule is working.
- **How:** Spawn a dotfiles mission. The hook is a few-line shell script; the analysis side is a periodic skill or `bd` bead.
- **Impact:** High — turns the skill library into an evolvable system rather than an opaque pile.
- **Confidence:** Likely — minor risk that log volume becomes annoying or that the analysis side never gets built.

**[Medium impact, Likely]** Establish an on-demand `/careful` (or equivalent) hook pattern that blocks destructive commands during sensitive work. Anthropic uses this exact construct: hooks that activate only when invoked, raising the safety floor for high-stakes sessions (e.g., editing prod, large refactors, working on git history). Kevin already has hard-coded denylists (workspace-mcp denylist, beads write block) but no user-toggleable "I'm doing something risky, raise the floor" mode.

- **What:** A skill or slash command like `/careful` that installs a session-scoped PreToolUse hook denying destructive Bash patterns (`rm -rf`, `git push --force`, `git reset --hard`, etc.) until explicitly turned off.
- **Why:** Distinct from blanket denials — the cost of always-on denial is friction in normal work; an on-demand mode only kicks in when Kevin acknowledges he's in a risky session.
- **How:** Dotfiles mission to design the toggle mechanism and the deny list.
- **Impact:** Medium — Kevin's existing safeguards already cover the most catastrophic cases.
- **Confidence:** Likely — value depends on how often Kevin works in genuinely risky modes.

### Workflows

**[High impact, Likely]** Codify the six dynamic-workflow patterns from the second harness post into Kevin's skill ecosystem. Kevin already runs at least one of these patterns explicitly — `/council` is a fan-out-and-synthesize / tournament hybrid. He uses subagent-driven-development implicitly. The other four (classify-and-act, adversarial verification, generate-and-filter, loop-until-done) appear in scattered places but lack a unified vocabulary. A reference skill that names these patterns and links to the canonical home of each (e.g., `/council` → tournament; `/loop` → loop-until-done; writing-proofreader → adversarial verification) would help Kevin and his subagents reach for the right pattern.

- **What:** A reference skill `/dynamic-workflow-patterns` (or merged into `/cc-configuration`) cataloging the six patterns, where each is already used in Kevin's setup, and decision rules for when to reach for which.
- **Why:** Pattern fluency accelerates design of new orchestrations — Kevin builds these by hand often.
- **How:** Dotfiles mission. The work is mostly documentation and cross-linking, not new code.
- **Impact:** High — pattern vocabulary compounds across future skill design.
- **Confidence:** Likely — value depends on Kevin internalizing the vocabulary; pure reference skills can become dead weight if never invoked.

Not a recommendation to change them — a recommendation to spawn a session that pressure-tests them.

- **Why:** Kevin's solo-founder context is the closest match to Fiona's "kill obsolete processes" advice — no one else will pressure-test his rituals.
- **How:** Schedule a focused session, not a mission.
- **Impact:** Medium — if rituals are well-calibrated, this is a no-op; if not, the gain is recurring.
- **Confidence:** Speculative — the engineering-org post is about a large team, not a one-person org.
